## 2. 背景与问题

### 2.1 市场背景

城市更新是城镇化进入存量时代的重要议题，各地政策频出且差异显著。城市更新项目的合规审查涉及多层级文件（国标/市级/区级），指标体系复杂（容积率、退线、奖励系数等），且政策时效性强。

### 2.2 现有问题

本项目要解决的真实痛点有两类：

**问题一：政策不熟的团队与新人需要低成本获得政策研判能力**
- 设计管理岗人员在项目初期对本地政策法规的掌握需要一定周期
- 本部门同事对相关政策条款的熟悉程度有待提升
- 此类经验知识目前主要积累于个人层面，尚未形成可沉淀、可复用的组织资产

**问题二：经验丰富但"错配"的团队需要快速补齐本地政策差**
- 外省团队空降到本地（如山东团队到北京），经验属于另一套政策体系
- 本质是信息问题：本地现行政策是什么、与原属地差异在哪

**额外风险：**
- 政策会过期（奖励类、试点类新规更新极快）
- 文件之间会冲突（同一指标国标/市级/区级口径不一致）

### 2.3 核心设计理念

> **把规则交给人工标定，把大模型关进受限的笼子里。**

在合规审查这类强确定性场景中，大语言模型最大的风险是"幻觉"——可能编造不存在的条款号、发文号或指标数值。本项目的解决方案是：
- 所有合规指标（容积率上限、退线距离、奖励系数等）由专业人员人工录入结构化规则库
- 大模型只承担两个简单的"翻译"工作：把用户说的话转成系统能看懂的数字（参数），以及把系统算出的结果转成人类能看懂的文字（报告）。具体怎么算、哪个是对的，全部由程序和规则库决定，大模型不参与判断
- 不参与任何数值判定与流程决策

## 3. 产品目标

### 3.1 核心目标

为城市更新项目提供**可自助、带依据的本地政策研判工具**，把合规研判从"依赖个别熟手且难以留痕"变为"有系统可查、有条款佐证"。

### 3.2 成功指标

| 指标 | 描述 |
|------|------|
| 功能可用性 | 核心功能（政策查询、合规校验）可正常演示并输出正确结果 |
| 结果可信度 | 每条结论均附带可核验的条款号与官方文件链接 |
| 覆盖范围 | 支持北京城市更新主要政策文件的结构化查询与校验 |
| 边界清晰 | 系统能够明确回复"暂无法判断"，不生成幻觉答案 |

### 3.3 产品定位

- **是**：辅助决策工具，解决信息层面问题（政策是什么、依据在哪、本地如何规定）
- **不是**：替代正式报建审查及专业规划师意见，不承诺解决物理资源与财务硬约束

## 4. 目标用户与角色

### 4.1 核心用户

| 用户类型 | 特征 | 痛点 |
|----------|------|------|
| **政策不熟的新人/实习生** | 刚入职或从其他业务线转入 | 缺少本地政策知识积累 |
| **跨地域经验团队** | 从外省转入本地，经验丰富但政策错配 | 原属地经验在本地失灵 |
| **设计管理岗** | 甲方企业中负责设计管理 | 需要花时间搜索调查政策 |

**核心考核目标**：方案不被推翻

### 4.2 次要用户

| 用户类型 | 使用场景 |
|----------|----------|
| 设计院方案负责人 | 接到任务书时先自查边界条件 |
| 责任规划师/区级更新专班 | 反向核对申报材料合规性 |

## 5. 用户故事

### 5.1 政策文件查询

| 故事 | 描述 |
|------|------|
| **US-01** | 作为一名政策不熟的新人，我想用自然语言提问某个政策手段能否在本项目使用，系统返回适用的文件、条款依据和官方链接 |
| **US-02** | 作为一名设计师，我想查询某项指标（如容积率）在本地现行文件中的具体数值和效力状态 |

### 5.2 合规校验

| 故事 | 描述 |
|------|------|
| **US-03** | 作为方案统筹，我想录入项目的片区属性和各地块指标，系统告诉我每块地是否合规、踩了哪些强制性条文 |
| **US-04** | 作为项目负责人，我想知道各地块规模之和是否超出片区总量上限，系统给出预警提示 |
| **US-05** | 作为审慎的用户，我想看到同一指标在不同层级文件中的差异对比，系统按从严原则给出建议 |

### 5.3 规模传导

| 故事 | 描述 |
|------|------|
| **US-06** | 作为资金测算人员，我想切换不同的容积率奖励政策，查看对应的可建规模差异及其条款出处（不涉及金额） |

### 5.4 政策更新监测

| 故事 | 描述 |
|------|------|
| **US-07** | 作为合规专员，我想定期检查规则库中的政策文件是否有更新，系统列出变更清单供我确认是否同步 |

### 5.5 流程导航

| 故事 | 描述 |
|------|------|
| **US-08** | 作为新人，我想知道本项目从立项到土地变更需要走哪些步骤、每步的依据是什么 |

## 6. 功能需求清单

### 6.1 模块一：政策文件查询

**需求描述**：

| 需求ID | 需求描述 | 优先级 | EARS类型 |
|--------|----------|--------|----------|
| **FR-01** | 当使用者用自然语言提问时，系统应抽取关键词在信源库中检索，返回文件名、发文号、生效日期、效力状态、官方原文链接 | P0 | Ubiquitous |
| **FR-02** | 当检索命中时，系统应返回原始记录，不允许由大模型生成文件名或发文号 | P0 | Ubiquitous |
| **FR-03** | 当检索未命中时，系统应明确回复"暂未收录，建议前往官方网站检索"并附官网入口 | P0 | Ubiquitous |
| **FR-04** | 系统应显示每条政策文件的效力状态标签（现行有效/已修改/已废止）和数据核验日期 | P0 | Ubiquitous |
| **FR-05** | 当使用者提问"某政策手段在本地能否适用"时，系统应回答适用条件、依据文件、操作流程，而非通用名词解释 | P1 | Event-driven |

### 6.2 模块二：合规校验（片区—地块两级）

**需求描述**：

| 需求ID | 需求描述 | 优先级 | EARS类型 |
|--------|----------|--------|----------|
| **FR-06** | 当使用者录入片区属性（更新类型、是否在特定范围、实施方式、区位）时，系统应判定适用哪几份政策文件 | P0 | Event-driven |
| **FR-07** | 当使用者录入或描述地块指标时，系统应将自然语言抽取为结构化参数，回填到表单供使用者确认 | P0 | Event-driven |
| **FR-08** | 当使用者确认参数后，系统应逐块判定用地指标是否踩线，输出 Allowed/Not Allowed 及依据条款 | P0 | Event-driven |
| **FR-09** | 当各地块规模累加超出片区总规模上限时，系统应预警"各期合计已超片区总量，超出 XX" | P0 | Event-driven |
| **FR-10** | 当同一指标在不同层级文件（国标/市级/区级）中查到不同数值时，系统应显式提示差异并按从严原则给出建议 | P0 | Unwanted |
| **FR-11** | 系统输出的每条结论应附带条款号，且条款号须通过核验（能在检索到的原文中匹配） | P0 | Ubiquitous |
| **FR-12** | 系统应支持两种输入方式：表单填数字、自然语言描述（由大模型抽取为结构化参数） | P1 | Optional |

### 6.3 模块三：规模传导

**需求描述**：

| 需求ID | 需求描述 | 优先级 | EARS类型 |
|--------|----------|--------|----------|
| **FR-13** | 给定片区与地块条件，当切换某条容积率奖励的启用状态时，系统应输出对应的可建规模差异及条款出处 | P0 | Event-driven |
| **FR-14** | 系统输出的数值只到规模为止，不涉及任何货币化计算（不计算造价、售价、租金等） | P0 | Ubiquitous |

### 6.4 模块四：政策更新监测

**需求描述**：

| 需求ID | 需求描述 | 优先级 | EARS类型 |
|--------|----------|--------|----------|
| **FR-15** | 系统应提供"检查政策更新"按钮，点击后执行定向爬虫并列出变更清单 | P0 | Event-driven |
| **FR-16** | 爬虫只负责发现变化并提醒，不自动改写规则库，是否更新由人工确认后手动执行 | P0 | Ubiquitous |

### 6.5 模块五：项目流程导航

**需求描述**：

| 需求ID | 需求描述 | 优先级 | EARS类型 |
|--------|----------|--------|----------|
| **FR-17** | 给定项目类型，系统应展示从立项到土地变更的主流程步骤，每步附带政策依据 | P1 | State-driven |
| **FR-18** | 当流程步骤涉及具体经办经验时，系统应标注"此环节涉及具体经办，建议咨询相关部门"，不编造隐性经验 | P0 | Unwanted |

### 6.6 输出增强：研判结果即汇报材料

**需求描述**：

| 需求ID | 需求描述 | 优先级 | EARS类型 |
|--------|----------|--------|----------|
| **FR-19** | 系统的每一项产出（合规结论、规模传导、流程路径）应整理为结构化、可直接用于汇报的格式 | P1 | Optional |

## 7. 非功能需求

### 7.1 性能要求

| 指标 | 要求 |
|------|------|
| 页面加载时间 | < 3秒 |
| 政策查询响应时间 | < 2秒 |
| 合规校验计算时间 | < 5秒（不含大模型调用） |
| 大模型调用超时 | 30秒后提示超时 |

### 7.2 可用性要求

| 要求 | 描述 |
|------|------|
| 数据隔离 | 多用户场景下，不同用户的数据应隔离存储 |
| 规则库版本管理 | 支持规则库更新的日志记录与回滚能力 |
| 异常处理 | 规则库为空、检索失败、模型调用失败时应有友好的错误提示和降级策略 |

### 7.3 数据要求

| 要求 | 描述 |
|------|------|
| 数据来源 | 规则库中的数值由专业人员人工录入，需提供录入工具 |
| 数据存储 | 本地文件存储（JSON/SQLite），为后续数据库迁移预留接口 |
| 适用城市 | 首个版本聚焦北京，后续可扩展至其他城市 |

### 7.4 安全要求

| 要求 | 描述 |
|------|------|
| 输入过滤 | 对用户输入进行基本的安全过滤，防止注入攻击 |
| 敏感信息 | 不在日志中记录用户上传的敏感项目数据 |

### 8.1 核心功能流程图

```
┌─────────────────────────────────────────────────────────────────────┐
│                         政策文件查询流程                              │
├─────────────────────────────────────────────────────────────────────┤
│  用户输入自然语言问题                                                │
│         ↓                                                            │
│  大模型抽取关键词                                                    │
│         ↓                                                            │
│  检索信源库 ──────────────────────────────────────┐                  │
│         ↓                                        │                  │
│   命中？ ──是──→ 返回文件名、发文号、生效日期、   │                  │
│         ↓         效力状态、官方链接              │                  │
│         ↓                                        │                  │
│        否                                        │                  │
│         ↓                                        ↓                  │
│  明确回复"暂未收录，建议前往官方网站检索" ←─────────────────────────┘
└─────────────────────────────────────────────────────────────────────┘
```

```
┌─────────────────────────────────────────────────────────────────────┐
│                        合规校验流程                                  │
├─────────────────────────────────────────────────────────────────────┤
│  输入：片区属性 + 地块指标                                            │
│         ↓                                                            │
│  ① 适用性判断 ── 规则引擎据片区属性判定适用文件                        │
│         ↓                                                            │
│  ② 参数抽取 ── 大模型将自然语言转为结构化参数                         │
│         ↓                                                            │
│  ③ 回填确认 ── 界面展示参数供用户确认修改                             │
│         ↓                                                            │
│  ④ 规则比对 ── 规则引擎命中规则库，检测多来源冲突                     │
│         ↓                                                            │
│  ⑤ 地块校验 ── 几何计算逐块判定 Allowed/Not Allowed                  │
│         ↓                                                            │
│  ⑥ 片区总量校验 ── 各地块规模求和，超上限则预警                      │
│         ↓                                                            │
│  ⑦ 条文检索+核验 ── 取出支撑条文，核验引用条款在原文                 │
│         ↓                                                            │
│  ⑧ 报告生成 ── 大模型将结构化结果转述为可读报告                       │
│         ↓                                                            │
│  输出：合规决策卡（地块结论 + 片区总量提示 + 规模传导）                │
└─────────────────────────────────────────────────────────────────────┘
```

## 10. 数据指标与埋点

### 10.1 核心业务指标

| 指标 | 描述 | 计算方式 |
|------|------|----------|
| 政策查询命中率 | 用户查询能命中信源库的比例 | 命中次数 / 总查询次数 |

### 10.2 用户行为埋点

| 事件 | 描述 |
|------|------|
| policy_query | 政策查询事件，记录查询词、命中结果 |
| compliance_check | 合规校验事件，记录输入参数、校验结果 |
| conflict_detected | 冲突检测事件，记录冲突指标、差异值 |
| rule_update | 规则库更新事件，记录更新人、更新内容 |

## 11. 验收标准

### 11.1 功能验收

| 需求ID | 验收条件 | 测试方法 |
|---------|----------|----------|
| FR-01 | 输入"北京容积率上限"，返回北京相关政策文件信息 | 手动测试 |
| FR-03 | 输入不存在的政策，返回"暂未收录"而非幻觉答案 | 边界测试 |
| FR-08 | 录入超出限值的容积率，返回 Not Allowed | 参数化测试 |
| FR-09 | 多个地块规模之和超过片区上限，弹出预警 | 边界测试 |
| FR-10 | 同一指标在国标/市级/区级有不同数值，显式提示差异 | 冲突测试 |
| FR-11 | 每条结论的条款号能在原文中匹配到 | 溯源验证 |
| FR-14 | 规模传导结果不包含任何金额计算 | 代码审查 |
| FR-16 | 爬虫不自动修改规则库，只生成变更清单 | 流程验证 |
| FR-18 | 流程导航中涉及隐性经验的步骤标注"建议咨询" | 边界测试 |

### 11.2 演示验收场景

系统可现场演示如下场景，形成完整闭环：

1. **政策查询**：自然语言提问，返回带发文号、生效日期、状态标签、官方链接的文件记录
2. **政策更新监测**：点击按钮现场跑出变更提醒清单
3. **两级合规校验**：选择示范片区自动填充，逐块录入分期地块指标，系统抽参回填、使用者确认，输出各地块合规决策卡
4. **片区总量预警**：地块规模合计超出片区上限时，系统弹出"各期合计已超片区总量"提示
5. **规模传导**：切换某条容积率奖励的启用与否，展示可建规模差异及其条款出处
6. **流程导航**：就示范项目展示从立项到土地变更的主流程路径
7. **冲突预警**：切换到多来源口径不一致的地块，系统弹出差异提示与从严建议
8. **诚实拒答**：输入超出覆盖范围的条件，系统明确回复"暂无法判断"

### 11.3 交付物要求

- 结构化合规规则库（不少于50条）
- 政策信源清单（不少于20份）
- 定向爬虫覆盖官方站点
- 边界测试用例覆盖冲突检测与拒答场景

## 12. 风险与依赖

### 12.1 项目风险

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 规则库数据准确性 | 高 | 专业人员录入需有复核机制 |

| 大模型幻觉 | 高 | 严格的人机分工 + 条款核验机制 |
| 首版功能 scope 过宽 | 中 | 聚焦MVP，迭代扩展 |

### 12.2 依赖项

| 依赖 | 描述 |
|------|------|
| 政策文件来源 | 需确认北京城市更新相关政策文件的公开程度 |
| 专业人员支持 | 规则库标定需要城市规划或政策领域专业人员参与 |
| 大模型 API | 需解决大模型调用的稳定性和成本问题 |
