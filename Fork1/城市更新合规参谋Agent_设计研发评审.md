## 一、评审议题

### 1.1 产品设计评审

| 议题 | 议题说明 | 需确认 |
|------|----------|--------|
| **功能Scope确定** | MVP功能范围划定 | 确认首版功能优先级，是否只做政策查询+合规校验+规模传导？ |
| **用户交互流程** | 自然语言输入→参数确认→结果输出 | 确认参数回填确认环节是否必要？是否可直接计算？ |
| **输出形式** | 合规决策卡格式 | 确认卡片包含哪些字段？是否需要支持导出？ |
| **多来源冲突处理** | 国标/市级/区级口径不一致时的处理策略 | 确认"从严原则"是否合理？是否需要支持用户选择？ |

### 1.2 技术架构评审

| 议题 | 议题说明 | 需确认 |
|------|----------|--------|
| **确定性流水线 vs Agent** | 为何采用确定性流水线而非自主Agent？ | 确认架构选择是否符合产品定位？ |
| **大模型选型** | 使用哪个大模型？本地部署还是API调用？ | 确认模型选择、成本预算、稳定性要求 |
| **数据存储方案** | 本地文件 vs 数据库 | 确认数据存储方案，是否需要提前设计数据库Schema？ |
| **检索方案** | 文本切片+向量检索的实现细节 | 确认检索精度要求、响应时间要求 |

### 1.3 数据准备评审

| 议题 | 议题说明 | 需确认 |
|------|----------|--------|
| **规则库数据来源** | 哪些政策文件需要结构化？ | 确认首批录入的政策文件范围（北京） |
| **数据录入工具** | 是否需要单独的开发管理后台？ | 确认规则库管理方式 |
| **信源库构建** | 政策文件元信息的采集与更新 | 确认数据来源、采集频率 |

## 四、风险点与缓解措施

### 4.1 高风险

| 风险 | 描述 | 缓解措施 |
|------|------|----------|
| **规则库数据错误** | 规则数值错一个，后续计算全错 | 专业人员录入 + 交叉复核机制 |
| **大模型幻觉** | 可能生成不存在的条款号 | 条款核验 + 诚实拒答机制 |
| **政策文件过期** | 规则库中的政策已废止但未更新 | 政策更新监测 + 人工维护 |

### 4.2 中风险

| 风险 | 描述 | 缓解措施 |
|------|------|----------|
| **功能scope过宽** | 首版想做太多功能导致延期 | 聚焦MVP，砍掉非必要功能 |
| **数据获取困难** | 政策文件无法完整获取 | 优先覆盖公开文件，标注覆盖范围 |
| **检索精度不足** | 检索不到相关内容 | 优化检索策略 + 人工补充同义词 |

### 4.3 低风险

| 风险 | 描述 | 缓解措施 |
|------|------|----------|
| **用户交互复杂** | 参数回填确认环节影响体验 | 提供表单直接输入作为备选 |
| **性能不达标** | 大模型调用超时 | 设置超时降级策略 |

## 五、技术方案建议（供参考）

### 5.1 推荐技术栈

| 组件 | 推荐方案 | 理由 |
|------|----------|------|
| 大语言模型 | GPT-4 API / Claude API | 免费额度充足，能力成熟 |
| 嵌入模型 | 中文轻量嵌入模型 | 笔记本可运行 |
| 检索引擎 | Qdrant / Milvus | 开源、向量化检索 |
| 规则引擎 | 自实现（Python） | 简单规则无需复杂引擎 |
| 界面框架 | Streamlit | 快速开发，无需前端 |
| 数据存储 | SQLite + JSON | 轻量、易于迁移 |
